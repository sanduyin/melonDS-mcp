# Infinite Space / 无限航路：汉化版图鉴案例

2026-09-14 在 Windows、DS 模式、解释器、软件渲染的本机 MCP DLL 上实测。以下是一个特定构建/运行阶段的证据，不是按 Game ID 自动执行的补丁。

## 适用证据

- 标题：`MUGEN KOURO`，游戏代码：`C6CJ`（日版基础）。
- 汉化构建标识：Time Team，20260824，v1.0，Chs。
- 实测 ROM 文件 SHA256：`e123f6b41a40b6ad8e1693f846ad82426d6b3017f6fbcdc8f742c138238ea290`。
- 普通存档实测大小：262144 字节。此大小不是所有 DS 游戏的通用要求。
- 原图鉴人物约4%，特殊天体约3%；修改前后的数值分布与 UI 一致。没有发布商业 ROM、个人存档或内存 dump。

## 已核实的字段

地址是 ARM9 数据视图里的内存地址，不是 `.sav` 文件偏移。在标题数据库及加载的港口场景中核实；其他运行阶段仍需重新读取。

| 表 | 首个标记地址 | 步长（字节） | 数量 | 字段宽度 | 写入策略 |
| --- | --- | ---: | ---: | ---: | --- |
| 舰船 | `0x021BFB10` | 88 (`0x58`) | 194 | 1 | 仅 `0→1`；保留已有 `2` |
| 舰载机 | `0x021C3E86` | 34 (`0x22`) | 28 | 1 | `0/1→2`，不改其他值 |
| 人物 | `0x021C50BA` | 92 (`0x5C`) | 147 | 1 | `0/1→2`，不是招募字段 |
| 特殊天体 | `0x021D4906` | 2 | 30 | 2 | `0→1`，不要额外写表前的计数/占位项 |

调用顺序例（Python 写法，MCP JSON 地址应传整数，不传 `"0x..."` 字符串）：

```python
table = await call("memory_table_read", address=0x021BFB10, stride=88, count=194, width=1)
# 先检查 table["values"] / counts 与当前 UI；未知值或构建不同先停止此配方。
result = await call("memory_table_patch", address=0x021BFB10, stride=88, count=194,
                    width=1, value=1, replace_values=[0], expected_sha256=table["sha256"])
```

`call` 表示客户端已解包结果的 MCP 调用函数，不是包里的现成全局函数。每一张表都必须先单独读取、核实，再传自己的新哈希。

## 此前金手指为什么无效

四组“欧版”候选地址比此构建实测地址大 `0x60`，并不对应正确标记。例如人物候选 `0x021C511A` 读出连续人物编号，舰船候选 `0x021BFB70` 落在其他属性字段。观察到这一偏差帮助定位，但不能据此对其他 ROM 或所有金手指统一减 `0x60`。

舰船原有三个值为2的条目，直接把全表写1会降级它们；本次验证保留了这三个2。人物标记与招募字段不是同一地址，未把全图鉴等同于全员加入。

## 持久性验证

先在内存中检查效果，再加载用户选定剧情栏位、复核/修改字段，通过游戏内保存菜单写入同一栏位。使用 `melonds_backup_export` 导出普通 `.sav`，随后关闭核心并冷启动，无即时存档、无金手指、无重复补丁。四类图鉴画面均为100%；重新读入剧情后表分布仍为：

- 舰船：191个1、3个2。
- 舰载机：28个2。
- 人物：147个2。
- 特殊天体：30个1。

剧情位置与金钱核对未变化；保存造成正常游戏计时增加。本案例不是通关档，也没有证明其他地区 ROM、其他汉化构建、DSpico 或其他真机兼容。

界面坐标不是可靠的通用脚本：舰载机类别解锁后可能出现额外菜单项。每次根据新截图确定按钮位置，触屏坐标相对下屏（0..255，0..191），不要拿拼接双屏图的全高坐标点击。
